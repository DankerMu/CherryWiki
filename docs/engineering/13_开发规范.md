# 13. 开发规范

## 1. 总体原则

1. 模块边界优先，禁止跨模块直接访问内部表和内部实现。
2. 所有知识内容必须经过 Canonical Wiki Repo。
3. 所有可检索对象必须有 ACL。
4. 所有后台任务必须幂等、可重试、可追踪。
5. 所有外部组件二开必须保留许可证声明。
6. 所有接口必须有 OpenAPI 或内部 API 文档。

## 3. 技术栈规范

> 已定型，不再留"或"。选型依据：与 Docmost Fork 基线对齐（NestJS + Fastify），减少技术分裂。

| 层 | 技术 | 备注 |
|---|---|---|
| 前端 | React + TypeScript + Vite | Cherry Web / Admin |
| API 后端 | NestJS + Fastify adapter | 与 Docmost Fork 技术栈统一 |
| ORM | Drizzle ORM | 类型安全、轻量、schema-first |
| Migration | Drizzle Kit (`drizzle-kit generate/migrate`) | 与 ORM 配套，schema 变更即迁移 |
| 队列 | Redis + BullMQ | Node.js Worker 直接消费 |
| Python Worker | Python 3.11+，独立进程 | 通过 cherry-api Job API 拉任务 + Redis distributed lock 协同 |
| 数据库 | PostgreSQL 16 (pgvector) | 单库，后续可读写分离 |
| 对象存储 | MinIO (S3 兼容) | 生产可替换为 AWS S3 / Cloudflare R2 |
| 向量 | pgvector (Phase 1) | Phase 4+ 可评估 Qdrant |
| 全文 | PostgreSQL FTS (Phase 1) | Phase 4+ 可评估 MeiliSearch |
| 图谱 | PostgreSQL graph tables (Phase 1) | Phase 4+ 可评估 Neo4j |
| 运行时 | Node.js 20 LTS | 配合 NestJS 10+ |

### 3.1 Python Worker 与 Node.js 协同

```text
cherry-api (NestJS)
  ├── POST /api/spaces/{id}/graphify/runs → 写 job 记录 → 发 BullMQ job
  │
graphify-worker (Python)
  ├── 轮询 cherry-api GET /internal/jobs/pending?type=graphify
  ├── 获取 job → Redis SETNX lock(job_id, worker_id, TTL=10min)
  ├── 执行 Graphify CLI
  ├── 上传结果到 MinIO
  └── PATCH /internal/jobs/{job_id}/complete → cherry-api 触发后续流水线
```

Python Worker 不直接操作 BullMQ（避免跨语言 SDK 兼容问题），通过 HTTP Job API + Redis lock 实现协同。Node.js Worker（ingestion/indexer/wiki-sync）直接消费 BullMQ。

## 4. TypeScript 规范

1. 开启 `strict`。
2. 禁止 `any`，必要时用 `unknown` 并做 runtime validation。
3. API DTO 使用 class-validator + class-transformer（NestJS 管道）；Drizzle schema 可通过 drizzle-zod 导出 zod schema 供跨层复用。
4. 所有 service 方法必须明确返回类型。
5. 不在 controller 中写业务逻辑。
6. 不在 repository 中写权限逻辑；权限由 service 或 policy 层统一处理。

## 5. Python Worker 规范

1. Worker 输入输出必须 JSON 化。
2. Graphify CLI 调用必须有 timeout、日志捕获、退出码处理。
3. 使用临时工作目录，不直接操作生产目录。
4. 输出文件必须校验大小、路径和 schema。
5. 任务必须幂等：同一 `run_id` 重试不会破坏已有发布版本。
6. Worker 不直接调用 Chat API。

## 6. API 规范

1. 所有外部 API 需要认证。
2. 内部 API 使用 service token，并限制网络访问。
3. 请求必须有 `request_id`。
4. 错误码统一大写蛇形：`PERMISSION_DENIED`。
5. 列表接口必须分页。
6. 删除接口默认软删除。

## 7. 数据库规范

1. 所有表包含 `created_at`，核心表包含 `updated_at`。
2. 多租户表必须包含 `tenant_id`。
3. 权限域表必须包含 `space_id`。
4. 迁移脚本不可手工跳版本。
5. 禁止在应用代码中拼接 SQL 字符串。
6. 大字段如 Markdown 可存 PostgreSQL，但大文件和 Graphify 输出应存对象存储。

## 8. 任务规范

任务状态：

```text
pending → running → succeeded
                 ↘ failed
pending → cancelled
```

复杂任务可扩展子状态：

```text
preparing → running_graphify → parsing_output → syncing_wiki → indexing → completed
```

每个任务必须记录：

- job_id。
- run_id。
- tenant_id。
- space_id。
- trigger_type。
- input_version。
- output_version。
- logs_uri。
- error_json。

## 9. Git 与分支规范

| 分支 | 说明 |
|---|---|
| `main` | 稳定分支。 |
| `develop` | 日常集成。 |
| `feature/*` | 功能开发。 |
| `fix/*` | 缺陷修复。 |
| `release/*` | 发版准备。 |
| `hotfix/*` | 紧急修复。 |

提交信息：

```text
feat(graphify): add graphify run parser
fix(auth): prevent cross-space retrieval
chore(deps): upgrade pgvector
```

## 10. PR 规范

PR 必须包含：

1. 变更说明。
2. 影响模块。
3. 测试结果。
4. 权限和安全影响。
5. 数据库迁移说明。
6. 截图或录屏，前端变更需要。
7. 许可证影响说明，涉及 Fork/外部代码时必须填写。

## 11. 文档规范

1. 新模块必须写模块需求和接口说明。
2. 重大架构决策必须写 ADR。
3. API 变更必须更新 OpenAPI。
4. 数据模型变更必须更新 schema 文档。
5. Graphify Wiki 页面格式变更必须更新 `wiki-core` 规范。

## 12. 日志规范

日志必须包含：

- request_id。
- job_id/run_id。
- tenant_id。
- space_id。
- user_id，如适用。
- error code。

禁止记录：

- API key。
- 用户密码。
- 模型完整请求中的敏感内容，除非有明确审计策略。

## 13. 代码审查重点

1. 是否绕过权限。
2. 是否把原始上传文件直接进入 Chat 检索。
3. 是否直接访问 Docmost 数据库。
4. 是否 Graphify 生成内容覆盖人工内容。
5. 是否任务不可重试。
6. 是否缺少审计。
7. 是否违反 AGPL 或企业功能授权边界。

## 14. Definition of Done

一个功能完成必须满足：

- 需求验收通过。
- 单元测试通过。
- 集成测试通过。
- 权限测试通过。
- 日志和审计完整。
- 文档更新。
- Docker 环境可运行。
- 无阻断级安全问题。
