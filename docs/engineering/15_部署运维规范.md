# 15. 部署与运维规范

## 1. 部署目标

1. Docker Compose 可启动 Phase 1 最小可用成品。
2. 支持服务独立扩缩容。
3. 支持数据持久化、备份和恢复。
4. 支持健康检查、日志和监控。
5. 支持未来迁移 Kubernetes。

## 2. 服务清单

| 服务 | 说明 |
|---|---|
| `cherry-web` | 用户前端。 |
| `cherry-admin` | 管理后台，可与 web 合并。 |
| `cherry-api` | 后端 API。 |
| `graphify-worker` | Graphify 后台任务。 |
| `ingestion-worker` | 上传资料解析。 |
| `wiki-sync-worker` | Docmost ↔ Canonical Wiki Repo 同步（Phase 2 启用）。 |
| `indexer-worker` | chunk、embedding、graph index。 |
| `url-fetcher-worker` | URL 抓取（独立容器，SSRF 隔离）。 |
| `docmost` | Wiki 协作编辑 UI（Phase 2 启用，Phase 1 不部署）。 |
| `docmost-db` | Docmost 独立 PostgreSQL（Phase 2 启用）。 |
| `docmost-redis` | Docmost 独立 Redis（Phase 2 启用）。 |
| `postgres` | 主数据库。 |
| `redis` | 队列和缓存。 |
| `minio` | 对象存储。 |
| `nginx` | 反向代理。 |

## 4. 环境变量

样例见 [`../ops/env.example`](../ops/env.example)。

关键变量：

```text
DATABASE_URL
REDIS_URL
MINIO_ENDPOINT
MODEL_API_BASE_URL
MODEL_API_KEY
ADMIN_OUTBOUND_PROBE_ALLOWLIST
DOCMOST_BASE_URL
DOCMOST_BRIDGE_SECRET
GRAPHIFY_WORKDIR
JWT_SECRET
APP_URL

# Phase 3+ Agent（cherry-api 容器内，详见 Doc 27 §4.8）
AGENT_ANTHROPIC_API_KEY        # Claude Code Agent API Key（必填）
AGENT_ANTHROPIC_BASE_URL       # 代理网关地址（可选，支持 Deepseek 等低成本替换）
AGENT_ANTHROPIC_MODEL          # 替换模型名（可选，如 deepseek-v4-flash）
CHERRY_AGENT_ROOT              # Agent 持久卷路径，推荐 /var/lib/cherry-agent
AGENT_PROCESS_IDLE_TIMEOUT_MS  # idle process kill，默认 86400000（24h）
AGENT_MAX_RESIDENT_PROCESSES   # 单 API 实例常驻 Claude 进程上限，默认 5
AGENT_SIGINT_GRACE_MS          # SSE 取消后 SIGINT→SIGKILL grace，默认 5000
AGENT_SESSION_RETENTION_DAYS   # stopped/failed session 保留天数，默认 7
CLAUDE_CODE_VERSION            # 锁定的 Claude Code 版本（Docker 构建时 pin）
```

`ADMIN_OUTBOUND_PROBE_ALLOWLIST` controls only admin-triggered outbound probes:
model connectivity tests and Docmost bridge health checks. By default these
probes allow `http`/`https` public targets and block localhost, private,
link-local, metadata, IPv6 ULA/link-local, and IPv4-mapped private targets
before making a request. Add comma-separated hostnames, IP addresses, or CIDRs
only for reviewed internal/self-hosted endpoints, for example:
`models.internal.example,10.20.0.0/16,fd00:1234::/48`. Keep this variable empty
in production when no private model or Docmost endpoint needs probing.

## 5. 健康检查

所有服务均在 Compose 中配置 `healthcheck`，依赖服务使用 `condition: service_healthy` 确保启动顺序。

### 5.1 服务健康端点

| 服务 | 检查方式 | Endpoint/命令 | interval |
|---|---|---|---|
| cherry-api | HTTP | `GET /api/health` | 30s |
| cherry-web | HTTP | `GET /` | 30s |
| docmost (Phase 2) | HTTP | `GET /api/health` | 30s |
| graphify-worker | HTTP | `GET :9090/health` | 30s |
| ingestion-worker | HTTP | `GET :9090/health` | 30s |
| indexer-worker | HTTP | `GET :9090/health` | 30s |
| wiki-sync-worker (Phase 2) | HTTP | `GET :9090/health` | 30s |
| mcp-gateway (Phase 4) | HTTP | `GET :8090/health` | 30s |
| postgres | CLI | `pg_isready -U cherrygraph` | 10s |
| redis | CLI | `redis-cli ping` | 10s |
| minio | HTTP | `GET /minio/health/live` | 30s |
| nginx | HTTP | `GET /` | 30s |

> **Phase 3+ Claude Code Agent 依赖**：cherry-api 容器需安装 Claude Code CLI（`npm install -g @anthropic-ai/claude-code@<pinned_version>`）。Docker `.env` 需配置 `AGENT_ANTHROPIC_API_KEY`（cherry-api 映射为子进程的 `ANTHROPIC_API_KEY`）。`CHERRY_AGENT_ROOT` 必须挂载为持久 volume（推荐容器内 `/var/lib/cherry-agent`），用于保存 workDir、隔离 HOME、`.claude` 会话和 `.instance_id`。API runtime 重启会关闭 live Claude child processes，但保留 `agent_sessions` metadata 和 workDir；同一 Chat session 的下一条消息会尝试 `--resume <provider_session_id>`。Claude Code 版本锁定在 Docker 镜像中（详见 Doc 27 §9）。cherry-api 通过 `spawn('claude', ...)` 调用，不需要独立容器。

### 5.2 Worker 健康检查设计

Worker 进程不仅依赖容器存活（PID 1），还需暴露应用层就绪状态。每个 Worker 启动一个轻量 HTTP 健康端口（`WORKER_HEALTH_PORT=9090`）：

```
GET :9090/health
```

响应：

```json
{
  "status": "healthy",
  "worker_type": "graphify-worker",
  "queue_connected": true,
  "last_heartbeat_at": "2026-04-28T12:00:00Z",
  "active_jobs": 1,
  "uptime_seconds": 3600
}
```

健康判定逻辑：

| 条件 | status |
|---|---|
| Redis 连接正常 + 最近 60s 有 heartbeat | `healthy` |
| Redis 连接正常 + heartbeat 超过 60s | `degraded` |
| Redis 连接断开 | `unhealthy` |

Compose `healthcheck` 仅检查 HTTP 200；cherry-api 的 `/api/admin/system/health` 聚合所有 Worker 状态供管理面板展示。

### 5.3 cherry-api /api/health 响应

```json
{
  "status": "healthy",
  "version": "0.2.0",
  "checks": {
    "database": "ok",
    "redis": "ok",
    "minio": "ok"
  }
}
```

非 200 时返回 503，Compose 判定为 unhealthy 并触发重启策略。

## 6. 数据持久化

必须持久化：

- PostgreSQL 数据。
- MinIO 数据。
- Redis AOF，至少任务队列需要。
- Canonical Wiki Repo。
- Graphify 输出。
- Docmost storage。

## 7. 备份策略

| 数据 | 频率 | 说明 |
|---|---|---|
| PostgreSQL | 每日全量 + WAL | 包含业务元数据和页面版本。 |
| MinIO | 每日同步 | 原始资料和 Graphify 输出。 |
| Wiki Repo | 每次 commit + 每日镜像 | 可直接 Git 备份。 |
| Docmost DB/storage | 每日 | 与 Wiki Repo 一起校验。 |
| Redis | 可选 | 队列可重建时无需长期保留。 |

## 8. 恢复流程

1. 恢复 PostgreSQL。
2. 恢复 MinIO。
3. 恢复 Wiki Repo。
4. 恢复 Docmost。
5. 启动 API 和 Worker。
6. 执行索引一致性检查。
7. 必要时重建索引。

### 8.1 恢复演练

| 项目 | 频率 | 说明 |
|---|---|---|
| 全量恢复演练 | 每月 1 次 | 从备份完整恢复到独立环境，验证数据完整性 |
| PostgreSQL 恢复 | 每月 1 次（含在全量中） | 恢复后验证 row count + random sample |
| MinIO 恢复 | 每月 1 次（含在全量中） | 恢复后验证文件 SHA256 |
| Wiki Repo 恢复 | 每月 1 次（含在全量中） | 恢复后验证 git log + page count |
| 索引重建验证 | 每季度 1 次 | 从零重建索引，对比 Chat 结果与生产一致性 |

演练结果记录到 `system_settings` 中，包含：演练时间、恢复耗时、验证结果、发现的问题。管理员面板展示最近一次演练状态。

## 9. 日志与监控

必须监控：

- API QPS、错误率、延迟。
- Chat 首 token 时间。
- 模型调用耗时和失败率。
- Graphify 任务耗时和失败率。
- 队列长度。
- 索引任务耗时。
- PostgreSQL 连接数。
- MinIO 存储容量。
- 权限拒绝异常波动。

## 10. 资源限制

### 10.1 容器资源配置

| 服务 | CPU limit | Memory limit | 说明 |
|---|---|---|---|
| cherry-api | 2.0 | 2GB | API 无状态，可水平扩展 |
| cherry-web | 0.5 | 512MB | 静态资源服务 |
| graphify-worker | 4.0 | 8GB | Graphify Python API + LLM 语义提取 memory intensive |
| ingestion-worker | 2.0 | 4GB | PDF/OCR 解析内存峰值 |
| indexer-worker | 2.0 | 4GB | Embedding 计算 |
| wiki-sync-worker | 1.0 | 1GB | 轻量同步 |
| postgres | 4.0 | 8GB | 视数据量调整 |
| redis | 1.0 | 2GB | 队列 + 缓存 |
| minio | 2.0 | 4GB | 视并发 IO 调整 |

### 10.2 业务层限制

| 限制项 | 默认值 | 可配置 |
|---|---|---|
| 单文件上传大小 | 50MB（Large 需审批：200MB） | 是（system_settings） |
| ZIP 解压后总大小 | 500MB | 是 |
| ZIP 最大嵌套层级 | 3 层 | 否 |
| 单文件解析超时 | 300s | 是 |
| Graphify run 超时 | 3600s | 是 |
| 单次 Graphify 最大输入页面 | 500 | 是 |
| graph.json 最大节点数 | 50000 | 是 |
| graph.json 最大边数 | 200000 | 是 |
| 单次输出总大小 | 1GB | 是 |

### 10.3 Graphify 输出保护

当新 run 输出与上一成功 run 偏差过大时，自动阻止激活：

| 检测项 | 阈值 | 行为 |
|---|---|---|
| 节点数骤降 | 新 / 旧 < 0.2（降 80%+） | → `quarantine` + 管理员通知 |
| 边数骤降 | 新 / 旧 < 0.2 | → `quarantine` + 管理员通知 |
| Wiki 页面数骤降 | 新 / 旧 < 0.3（降 70%+） | → `quarantine` + 管理员通知 |
| 节点数骤增 | 新 / 旧 > 5.0（增 5 倍+） | → `quarantine`（可能输入异常） |

管理员可在 Admin Console 查看对比详情后 `force_accept` 或 `discard`。

## 11. 队列隔离

BullMQ 按职责拆分队列，避免大任务阻塞小任务：

| 队列名 | 消费者 | 说明 |
|---|---|---|
| `graphify:small` | graphify-worker | 增量更新（input_scope ≤ 50 页） |
| `graphify:large` | graphify-worker | 全量重建（input_scope > 50 页或 mode=rebuild） |
| `ingestion` | ingestion-worker | 文件解析 |
| `indexer` | indexer-worker | chunk + embedding + snapshot 构建 |
| `docmost-sync` | wiki-sync-worker | Docmost ↔ Repo 同步（Phase 2） |
| `system` | cherry-api | 轻量系统任务（一致性检查、缓存清理） |

队列优先级（数字越小优先级越高）：

```text
ingestion (priority: 50)     — 用户上传感知快
indexer (priority: 80)       — 需要等 ingestion 完成
graphify:small (priority: 100) — 增量更新常规优先
docmost-sync (priority: 100) — 常规同步
system (priority: 150)       — 后台维护
graphify:large (priority: 200) — 大任务低优先级，不阻塞其他
```

Worker 并发配置：

| Worker | 并发数 | 说明 |
|---|---|---|
| graphify-worker | 1（同一 Space 互斥） | Redis lock 确保 |
| ingestion-worker | 5 | 多文件并行解析 |
| indexer-worker | 3 | embedding 计算资源密集 |
| wiki-sync-worker | 2 | Docmost Bridge 限流 |

## 13. Graphify Worker 运维

1. 每个 Worker 限制并发（Redis distributed lock per Space）。
2. 大型 Space 走 `graphify:large` 队列。
3. 任务超时自动失败（默认 3600s）。
4. 输出保护：骤降/骤增时 quarantine（见 §10.3）。
5. Worker 容器安全配置（见安全文档 §5.1）。
6. 工作目录使用 tmpfs，每次 job 结束自动清理。
7. 日志持久化到 MinIO `logs/graphify/{run_id}/`。

## 14. 升级策略

1. 先升级测试环境。
2. 备份 DB、Wiki Repo、MinIO。
3. 执行 migration dry-run。
4. 滚动升级 API 和前端。
5. 暂停 Worker 后升级 Worker。
6. 恢复 Worker 并执行索引一致性检查。

## 15. 故障处理

### 12.1 Graphify 失败

- 查看 run log。
- 检查输入 corpus。
- 检查模型调用。
- 重试。
- 如多次失败，回滚到上一 graph 版本。

### 12.2 Docmost 同步失败

- 检查 Bridge token。
- 检查页面 Frontmatter。
- 进入 sync_pending 队列重试。
- 必要时手动导出 Markdown 合并。

### 12.3 Chat 引用错误

- 查看 retrieval debug。
- 检查 page_version。
- 检查 chunk 与 graph ACL。
- 重新索引页面。

## 16. Phase 1 部署验收

1. `docker compose up -d` 后所有 Phase 1 服务健康（不含 Docmost）。
2. 可以登录 Cherry Web。
3. 可以上传资料并完成 Graphify。
4. Cherry Web 只读 Wiki 可浏览已发布页面。
5. 可以 Chat 并返回 Wiki 页面引用。
6. 停止某个 Worker 后任务不会丢失。
7. 重启后已发布知识仍可检索。

> Phase 2 部署验收额外要求：Docmost 可登录、页面编辑可同步回 Repo。
