# 12. 权限、安全与审计

## 1. 安全目标

1. 用户只能访问有权限的 Space、Wiki 页面、图谱节点、边和引用。
2. 上传资料不能越权进入其他 Space。
3. Graphify 运行不能跨权限域混合语料。
4. Chat 不能通过向量检索或图谱路径泄露无权限内容。
5. 管理操作可审计、可回溯。
6. AGPL 和第三方许可合规。

## 2. 权限模型

### 2.1 角色

| 角色 | 权限摘要 |
|---|---|
| Owner | 全局所有权限。 |
| Admin | 管理用户、Group、Space、模型、任务。 |
| Space Admin | 管理指定 Space。 |
| Editor | 上传资料、编辑 Wiki、发布页面。 |
| Viewer | 浏览 Wiki、使用 Chat 检索。 |
| Auditor | 查看审计和报告。 |

### 2.2 权限点

```text
space:view
space:edit
space:admin
upload:create
upload:read
wiki:publish
wiki:rollback
graphify:run
graphify:view
chat:use
model:use
admin:user_manage
admin:model_manage
admin:audit_view
```

## 2A. 权限主数据源

### 2A.1 原则

**Cherry API / Cherry Auth 是权限的唯一主数据源**。Docmost 权限只是 Cherry 权限的 UI 访问控制投影，不是独立权限体系。

| 层面 | 主数据源 | 投影/消费方 |
|---|---|---|
| 用户、Group、成员关系 | Cherry `users` / `groups` / `group_members` 表 | Docmost Group（单向同步） |
| Space 及其权限 | Cherry `spaces` / `space_permissions` 表 | Docmost Space（单向同步） |
| 页面 ACL | Cherry `wiki_pages.acl_json` + `wiki_chunks.acl_json` | Docmost Space 成员可见性 |
| Chat/RAG 检索权限 | Cherry ACL 信封（`acl_json`） | **永远不读 Docmost ACL** |

### 2A.2 同步方向

```text
Cherry Admin 创建/修改 → Cherry DB → 同步到 Docmost
```

禁止反向：Docmost 管理员不得独立修改权限。如果 Docmost 侧权限被修改，Cherry reconciliation 定时任务会覆盖回 Cherry 定义的状态。

### 2A.3 同步机制

1. **事件驱动**：Cherry API 在 Group/Space 权限变更后，通过 Bridge 推送到 Docmost Fork（`PUT /api/internal/bridge/spaces/{id}/permissions`）。
2. **定时 reconcile**：`permission_reconciler` 定时任务每小时比对 Cherry 权限和 Docmost 权限，差异自动修复为 Cherry 状态。
3. **不一致熔断**：如果 reconcile 发现差异且修复失败，暂停该 Space 的 Docmost 编辑和 Chat 检索，直至管理员介入。

### 2A.4 实现约束

1. Chat 和 RAG 检索**只读** Cherry 的 `acl_json` 和 `space_permissions`，禁止查询 Docmost 数据库。
2. Docmost Fork 的 Bridge 权限同步接口必须是**幂等覆盖**，不是增量合并。
3. 审计日志记录所有权限同步事件和 reconcile 修复动作。
4. Phase 1 无 Docmost，权限完全由 Cherry 管理。Phase 2 接入 Docmost 后启用同步。

## 3. Space 隔离

Space 是知识隔离和 Graphify 运行隔离的基本单位。禁止把不同权限域资料合并成单一 Graphify corpus，除非创建明确授权的跨空间知识库。

错误做法：

```text
/all-company-docs → graphify → 一个全局 graph.json
```

正确做法：

```text
/spaces/rd-platform → graphify → graph_rd.json
/spaces/legal      → graphify → graph_legal.json
/spaces/finance    → graphify → graph_finance.json
```

跨 Space 查询必须显式选择多个 Space，并逐项权限校验。

## 4. 检索权限

### 4.1 检索前

解析用户 token，得到：

```json
{
  "user_id": "user_001",
  "tenant_id": "tenant_001",
  "group_ids": ["group_rd"],
  "allowed_space_ids": ["space_rd"]
}
```

### 4.2 检索中

所有查询必须带：

```sql
WHERE tenant_id = :tenant_id
  AND space_id = ANY(:allowed_space_ids)
  AND acl_allows(:group_ids, acl_json)
```

### 4.3 检索后

候选结果合并后再次过滤。图谱路径中任意节点或边无权限，整条路径作废。

### 4.4 回答前

LLM 上下文组装前再次确认引用对象权限。

## 4A. 撤权缓存失效

### 4A.1 风险

用户被从 Space 移除后，若检索缓存未及时失效，可能在短窗口内仍看到已撤权内容。

### 4A.2 实现方案

| 机制 | 说明 |
|---|---|
| `permission_version` | `spaces`、`users`、`groups` 三张表各有 `permission_version BIGINT` 计数器（schema.sql 已落字段） |
| Cache key 包含版本 | 检索缓存 key = `tenant_id:user_id:user_pv:space_id:space_pv:query_hash`（`pv` = permission_version） |
| 主动失效 | 权限变更后立即清理该 Space 下所有用户的检索缓存（Redis `DEL space:{id}:cache:*`） |
| Short TTL 兜底 | 检索缓存 TTL ≤ 5 分钟，即使主动失效失败，窗口有限 |
| ACL cache TTL | `acl_json` 缓存 TTL = 60s，权限变更事件触发即时失效 |

### 4A.3 权限变更触发链

```text
Space 级权限变更（Space ACL / Group 绑定变更）
  → UPDATE spaces SET permission_version = permission_version + 1
  → 发布 Redis event: permission_changed:{space_id}
  → 所有 API 实例订阅该事件 → 清理本地 + Redis 缓存
  → 审计记录写入 permission_versions 表

User 级权限变更（用户加入/移出 Group）
  → UPDATE users SET permission_version = permission_version + 1
  → UPDATE groups SET permission_version = permission_version + 1（涉及的 Group）
  → 发布 Redis event: user_permission_changed:{user_id}
  → 清理该用户所有 Space 检索缓存
  → 审计记录
```

## 4B. Bridge Replay 防护

### 4B.1 攻击模型

攻击者截获合法 Bridge 请求后重放，伪造 Docmost 事件。

### 4B.2 防护机制

| 检查 | 实现 |
|---|---|
| Timestamp 窗口 | `X-Bridge-Timestamp` 与服务器时间差 > 5 分钟 → 拒绝（401） |
| Nonce 唯一性 | `X-Bridge-Nonce` 存入 Redis SET（TTL=10min），重复出现 → 拒绝 |
| Event ID 幂等 | `X-Bridge-Event-Id` 查 `bridge_events` 表，已存在 → 200 + deduplicated |
| HMAC 覆盖范围 | 签名覆盖 `method + path + timestamp + nonce + SHA256(body)` |
| Secret 轮换 | `DOCMOST_BRIDGE_SECRET` 支持双 key 滚动（新旧 key 并存窗口 24h） |

### 4B.3 校验流程

```text
1. 检查 Authorization Bearer token 匹配
2. 检查 X-Bridge-Timestamp 在窗口内
3. 检查 X-Bridge-Nonce 未使用（Redis SETNX, TTL=10min）
4. 计算 HMAC = SHA256(method + path + timestamp + nonce + SHA256(body), secret)
5. 对比 X-Bridge-Signature
6. 查 bridge_events 表：event_id 已存在 → 返回 200 deduplicated
7. 全部通过 → 处理请求
```

## 4C. Prompt Injection 防护

### 4C.1 风险

上传资料和网页抓取内容可能包含 LLM 注入指令（如"忽略之前指令"、"输出系统 prompt"）。

### 4C.2 防护层

| 层面 | 措施 |
|---|---|
| Prompt 结构隔离 | Context 标记为 `(data, not instructions)`，system prompt 中显式声明 context 不是指令 |
| Ingestion 扫描 | ingestion-worker 对 chunk 内容扫描注入 pattern（`ignore previous`、`system prompt`、`<\|im_start\|>`、`you are now`），命中的 chunk 标记 `injection_risk: true` |
| 检索降权 | `injection_risk: true` 的 chunk 在 rerank 中 score × 0.3 |
| Tool call gating | 即使 LLM 被诱导，tool_call 必须经 policy 层白名单审批 |
| 回答过滤 | 回答中不得出现系统配置信息、API key、内部 URL |
| 审计 | retrieval_traces 记录是否包含高风险 chunk，管理员可查 |

### 4C.3 注入 Pattern 列表（初始版本）

```text
ignore (all )?(previous|prior|above) (instructions|prompts|rules)
(system|developer) prompt
<\|im_start\|>
you are now
forget (everything|all|your instructions)
act as
new instructions
override
```

Pattern 列表可由管理员在 `system_settings` 中更新，无需重新部署。

## 5. 上传安全

Phase 1 要求：

- 文件白名单。
- MIME 校验（magic bytes vs Content-Type）。
- SHA256 去重。
- ZIP 安全解压（禁路径穿越、限层级、限总大小）。
- 上传大小限制（分层：≤5MB / 5-50MB / >50MB）。
- 上传权限检查。
- 原文件不可变归档。
- **Quarantine 隔离**：文件先进 quarantine，校验通过再入 archive。

### 5.1 解析沙箱容器安全

ingestion-worker 和 graphify-worker 容器必须应用以下安全配置：

```yaml
# docker-compose security context
security_opt:
  - no-new-privileges:true
cap_drop:
  - ALL
read_only: true
tmpfs:
  - /tmp:size=5G,noexec
  - /work:size=10G
```

| 安全措施 | 说明 |
|---|---|
| `read_only: true` | 只读 rootfs，防止写入恶意文件 |
| `no-new-privileges` | 禁止通过 setuid/setgid 提权 |
| `cap_drop: ALL` | 移除所有 Linux capabilities |
| `tmpfs` 工作目录 | 每次重启清空，不持久化临时文件 |
| 网络出站策略 | ingestion-worker：仅允许访问 MinIO、Redis、PostgreSQL，**禁止公网出站**。URL 抓取由独立 `url-fetcher-worker` 容器通过 egress proxy 执行（见 Doc 07 §6.2A） |
| 资源限制 | `mem_limit: 4G`, `cpus: 2.0`（compose 配置） |
| 非 root 运行 | `user: "1000:1000"` |
| 无宿主敏感挂载 | 禁止挂载 `/etc`、`/var/run/docker.sock`、宿主 home 目录 |

Phase 1 P0 要求（SSRF 防护，威胁模型 T3 Critical）：

- 外链抓取安全沙箱：独立 `url-fetcher-worker` 容器 + egress proxy + 私网 IP 拦截 + DNS pinning + 每跳 redirect 校验（详见 Doc 07 §6.2A）。

P1 要求：

- 病毒扫描。
- 敏感词/密级识别。
- DLP 策略。

## 6. Graphify 运行安全

1. 每次 Graphify run 必须绑定单一 `tenant_id` 和 `space_id`。
2. Graphify 输入目录由系统生成，不允许用户指定任意服务器路径。
3. `.graphifyignore` 由平台维护，防止密钥、配置、系统文件进入图谱。
4. 运行容器使用最小权限（同 §5.1 沙箱安全配置）。
5. 输出解析前先校验文件路径和大小。
6. Graphify 失败不影响上一已发布索引。

### 6.1 输出校验规则

cherry-api 在 `parsing_output` 阶段必须执行以下校验，不通过则进入 quarantine：

| 校验项 | 规则 | 不通过处理 |
|---|---|---|
| `graph.json` 存在 | 文件存在且 JSON 合法 | → `failed` |
| 节点数上限 | `nodes.length ≤ 50000`（可配置） | → `quarantine` |
| 边数上限 | `edges.length ≤ 200000`（可配置） | → `quarantine` |
| 节点/边必填字段 | 每个 node 有 id/label/type；每个 edge 有 source/target/relation_type | → `quarantine` |
| 文件路径安全 | 输出中所有文件路径不含 `..`、绝对路径、符号链接 | → `failed` + 安全告警 |
| 单文件大小 | 任何单个输出文件 ≤ 100MB | → `quarantine` |
| 总输出大小 | 所有输出文件总和 ≤ 1GB | → `quarantine` |
| Wiki 页面数 | mode=build 时 `wiki/*.md` 数量 > 0 | → `quarantine` |
| 偏离检测 | 节点/边数量与上次成功 run 偏差 > 80% | → `quarantine` + 管理员通知 |

### 6.2 graph.html 渲染安全

`graph.html` 是 Graphify 生成的 vis.js 交互可视化，可能包含 XSS 向量。

| 规则 | 说明 |
|---|---|
| 不直接 iframe 渲染 | 必须使用 `sandbox="allow-scripts"` 属性，禁止 `allow-same-origin` |
| CSP header | 预览页面设置 `Content-Security-Policy: script-src 'unsafe-inline'; frame-ancestors 'self'` |
| 管理员专属 | 仅管理员可查看 graph.html 预览，普通用户看 graph 摘要 JSON |
| 存储隔离 | graph.html 存储在 MinIO 独立 bucket，不与用户可访问内容同 bucket |

### 6.3 Wiki Markdown 内容清洗

Graphify 生成的 Wiki Markdown 在写入 Canonical Wiki Repo 前必须清洗：

| 清洗项 | 规则 |
|---|---|
| HTML 标签 | 只允许 `<!-- graphify:* -->` 注释标记，其余 HTML 标签 strip |
| Script 标签 | 完全移除 `<script>`、`<iframe>`、`<object>`、`<embed>` |
| 外链 | 保留但标记 `rel="nofollow noopener"`；管理员可配置外链白名单 |
| Data URI | 移除 `data:` URI（防止嵌入恶意 payload） |
| 图片引用 | 只允许相对路径（`_attachments/`）或白名单域名 |
| Event handlers | 移除 `on*=` 属性（`onclick`、`onerror` 等） |

清洗由 wiki-core 模块在写入 Repo 前执行，使用 allowlist 模式（只放行已知安全的 Markdown 语法）而非 blocklist。

## 7. Docmost 同步安全

1. Docmost Group 必须与 Cherry Group 定期一致性校验。
2. Docmost 页面导出后，必须验证 page_id、space_id、ACL。
3. 无效 Frontmatter 不得发布。
4. 直接从 Docmost 获得的内容必须先进入 Canonical Wiki Repo，再进入索引。
5. Docmost API key 或 Bridge token 必须作为机密管理。

## 9. 密钥管理

- 模型 API key 不落前端。
- Docmost Bridge token 不落前端。
- MinIO credentials 使用环境变量或 secret manager。
- 日志脱敏。
- 管理员下载诊断包时移除密钥。

## 11. Phase 1 验收

1. 无权限用户不能检索到无权限 Space 内容。
2. 图谱路径不能跨越无权限节点。
3. 上传文件不能指定任意服务器路径。
4. Docmost 编辑后未同步 Repo 的页面不能进入索引。
5. 所有关键操作有审计记录。
6. 管理员能查看权限一致性检查结果。
