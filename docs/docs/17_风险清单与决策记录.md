## 2. 架构决策记录摘要

### ADR-001：选择 Fork Cherry Studio 社区版并重构 Web

决策：采用路线 A。  
理由：保留 Cherry 产品体验和开源生态，满足 Web 多用户和 Docker 部署。  
代价：需要处理 AGPL、Electron 架构重构和服务端化。

### ADR-002：Graphify Wiki 是唯一知识源

决策：上传原文件、Docmost 页面和 Graphify 输出都必须进入 Canonical Wiki Repo，只有 Published Wiki 可检索。  
理由：避免多知识源不一致，提升引用清晰度。  
代价：上传后不能即时用原文件问答，需完成生成/发布/索引流程。

### ADR-003：Docmost 是协作壳层，不是独立知识源

决策：Docmost 提供编辑和页面体验，最终内容回写 Repo。  
理由：满足多人修订，同时保持 Graphify Wiki 唯一源。  
代价：需要 Bridge 和同步一致性机制。

### ADR-004：Graphify 后台自动任务化

决策：Cherry Web 后台自动调用 Graphify CLI/Worker。  
理由：用户不需要手工操作 CLI，平台能审计和编排。  
代价：需要任务队列、容器环境、输出解析和失败恢复。

### ADR-005：MVP 用 PostgreSQL 图谱表，Neo4j 可选

决策：MVP 不强制 Neo4j。  
理由：降低部署复杂度。  
代价：复杂图查询性能和语法能力有限。

### ADR-006：MVP 用 pgvector，后续可替换 Qdrant

决策：MVP 优先 PostgreSQL + pgvector。  
理由：简化部署。  
代价：大规模向量性能有限。

## 3. 待决问题

| ID | 问题 | 建议 |
|---|---|---|
| Q1 | Docmost 是否采购 Enterprise？ | 若生产强依赖 API/MCP，建议采购或明确 Fork。 |
| Q2 | 是否需要商业授权 Cherry？ | 如不希望履行 AGPL 网络源码义务，应谈商业授权。 |
| Q3 | Graphify 输出 schema 是否稳定？ | graph-core 做适配层，不直接把原 JSON 当业务 schema。 |
| Q4 | 是否需要审批流？ | MVP 只做发布状态；P1 做审核流。 |
| Q5 | 是否使用 Neo4j？ | 等 graph tables 性能瓶颈出现后再引入。 |
