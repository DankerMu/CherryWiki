# 01. 方案总览与边界

## 1. 项目背景

目标是在现有 Cherry Studio 社区版基础上 Fork 并重构为 Docker 化 Web 端，同时吸收企业版中“集中模型、共享知识库、用户/分组/权限、后台管理、私有部署”等能力形态。知识层不采用独立人工 Wiki，而以 Graphify 生成和维护的 Wiki 作为唯一知识源；Docmost 被选为多人协作和页面编辑外壳。

本项目的核心不是“聊天 + 文档检索”，而是一个完整知识生产、维护、索引、问答闭环：

```text
上传资料/人工修订
  → 归档与解析
  → Graphify Wiki 生成/增量更新
  → Docmost 页面同步与人工校订
  → Graphify 图谱更新
  → Cherry Web GraphRAG 检索问答
  → 引用回 Wiki 页面和图谱路径
```

## 2. 业务目标

### 2.1 主要目标

1. 提供一个可 Docker 部署的 Cherry Studio Web 端。
2. 支持多用户、分组、空间、知识库权限与审计。
3. 使用 Graphify Wiki 作为唯一知识源。
4. 使用 Docmost 提供 Wiki 网页、多人编辑、页面历史、附件、Spaces 和权限体验。
5. 上传资料后自动归档、解析、分类、生成 Wiki 草稿或更新建议。
6. 后台自动运行 Graphify，生成 `wiki/`、`graph.json`、`GRAPH_REPORT.md`，并导入平台索引。
7. Cherry Web 聊天端与 Graphify 强耦合，支持 Vector + BM25 + GraphRAG 混合检索（Phase 1 静态 RAG；Phase 3+ Claude Code Agent 深度路径）。
8. 回答必须提供 Wiki 页面引用、图谱路径或证据链。

### 2.2 次要目标

1. 保留 Cherry Studio 的多模型、多会话、Markdown 渲染、MCP、Agent 等体验。
2. 内部工具走 CLI（graphify/cherrydb/cherrywiki），MCP 仅用于第三方外部集成。
3. 支持知识质量治理：低置信关系审核、重复页面合并建议、冲突知识提示。
4. 支持后续接入 Neo4j、OpenSearch、Qdrant 等独立后端。

## 3. 非目标

以下内容不作为首期目标：

1. 不直接把 Electron App 原样暴露为 Web 页面。
2. 不让聊天端直接检索原始 PDF、DOCX、上传文件作为知识源；原文件只作为证据归档和再生成输入。
3. 不把 Docmost 作为独立人工 Wiki；Docmost 是 Graphify Wiki 的协作编辑界面。
4. 不在首期实现复杂工作流引擎、审批流、全文知识审计 AI 等高级治理。
5. 不保证与 Cherry Enterprise 闭源能力完全一致；只实现同类能力。
6. 不在首期实现所有 Cherry Studio 桌面端本地能力，例如本地窗口、全局快捷键、桌面小程序等。

## 4. 核心术语

| 术语 | 定义 |
|---|---|
| Cherry Web | Fork Cherry Studio 后重构出的 Web 前端和服务端平台。 |
| Graphify Wiki | Graphify 输出并由人工修订维护的 Wiki 页面体系，是唯一知识源。 |
| Canonical Wiki Repo | Graphify Wiki 的规范化 Markdown 仓库，负责版本化、冲突合并和回滚。 |
| Docmost Shell | Docmost 作为 Graphify Wiki 的多人编辑、页面历史、权限和附件 UI 壳。 |
| Source Archive | 上传原始文件归档库，保存 PDF、Word、图片、网页快照等原始证据。 |
| Published Wiki | 已发布、可被 Cherry Web 检索问答的 Wiki 页面版本。 |
| Graphify Run | 一次后台 Graphify 任务，输入为 Canonical Wiki Repo 或上传材料，输出为图谱和 Wiki 更新。 |
| GraphRAG | 结合向量、关键词、图谱节点、关系路径和社区摘要的检索增强生成。 |

## 5. 关键边界

### 5.1 Graphify Wiki 与 Docmost 的边界

Docmost 不直接成为知识真相的最终存储。它承担以下职责：

- 页面浏览。
- 多人实时编辑。
- 页面历史。
- 评论和修订讨论。
- 附件呈现。
- Spaces 和权限 UI。

Graphify Wiki 承担以下职责：

- Markdown 规范化内容。
- 图谱化抽取。
- 页面目录与主题结构。
- 可被 LLM 使用的索引材料。
- 与 GraphRAG 绑定的引用源。

因此，任何 Docmost 页面变更都必须通过 `docmost-bridge` 回写到 Canonical Wiki Repo，再触发索引更新。反之，任何 Graphify 生成的新页面或页面更新，也必须通过差异合并后同步到 Docmost。

### 5.2 上传原文与唯一知识源的边界

上传文件不是直接问答源。上传文件的状态为：

```text
raw file → immutable archive → parsed artifact → Graphify extraction → wiki draft/proposal → published wiki → indexable source
```

聊天检索只能使用 `published wiki` 及其派生索引。回答可以引用原文件作为证据，但引用入口应优先落在 Wiki 页面，再从页面展示原文件证据。

### 5.3 Graphify 自动生成与人工修订的边界

Graphify 不能直接覆盖人工修订。页面分为三种区域：

1. `managed_by_graphify`：Graphify 可自动更新。
2. `human_curated`：人工维护，Graphify 不得覆盖。
3. `proposed_update`：Graphify 生成的候选更新，需要合并或审核。

推荐页面内部使用 Frontmatter 和块级标记：

```markdown
---
page_id: wiki.auth.sso
source: graphify
last_graphify_run_id: gf_20260427_001
curation_status: published
---

<!-- graphify:managed:start -->
自动生成摘要。
<!-- graphify:managed:end -->

<!-- human:curated:start -->
人工补充说明。
<!-- human:curated:end -->
```

## 6. 基础技术事实

项目设计基于以下外部事实：

- Cherry Studio 社区版 README 将其定位为支持 Windows、macOS、Linux 的桌面客户端，并支持多 LLM 服务商、本地模型、文档处理、MCP 等功能。
- Cherry Studio README 中说明企业版方向包含统一模型管理、企业知识库、细粒度访问控制、私有部署和稳定后端服务。
- Cherry Studio 社区版使用 AGPL-3.0 许可，网络服务化 Fork 需合规。
- Graphify 可把代码、文档、论文、图片、音视频等目录转为知识图谱，输出 `graph.html`、`GRAPH_REPORT.md`、`graph.json`、缓存，并支持 `--wiki`、`query`、`path`、`explain`、`--update`、`--mcp` 等能力。
- Docmost 是开源协作 Wiki，支持实时协作、Spaces、权限、Groups、附件、导入导出、Docker 部署；其 API/MCP 在官方文档中标注为企业功能。

详细来源见 [资料依据与外部来源](../project/19_资料依据与外部来源.md)。

## 7. 总体成功标准

项目达到以下条件可以认为方案成功：

1. 一个 Docker Compose 可启动完整平台。
2. 管理员可以创建用户、分组、知识空间和模型配置。
3. 用户可以上传资料，系统能自动归档、解析、生成或更新 Graphify Wiki。
4. 用户可以在 Docmost 页面中人工修订 Wiki。
5. 页面修订可以同步回 Canonical Wiki Repo，并触发 Graphify 增量更新。
6. Cherry Web 聊天可以基于 Wiki 和图谱回答，并给出可点击引用。
7. 权限隔离可验证：用户无法在检索、引用、图谱路径中看到无权限空间内容。
8. 后台可查看每次 Graphify 运行状态、成本、输出、错误和索引版本。
