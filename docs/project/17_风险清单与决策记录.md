## 2. 架构决策记录摘要

### ADR-001：选择 Fork Cherry Studio 社区版并重构 Web

决策：采用路线 A。  
理由：保留 Cherry 产品体验和开源生态，满足 Web 多用户和 Docker 部署。  
代价：需要处理 Electron 架构重构和服务端化。

### ADR-002：Graphify Wiki 是唯一知识源

决策：上传原文件、Docmost 页面和 Graphify 输出都必须进入 Canonical Wiki Repo，只有 Published Wiki 可检索。  
理由：避免多知识源不一致，提升引用清晰度。  
代价：上传后不能即时用原文件问答，需完成生成/发布/索引流程。

### ADR-003：Docmost 是协作壳层，不是独立知识源

决策：Docmost 提供编辑和页面体验，最终内容回写 Repo。  
理由：满足多人修订，同时保持 Graphify Wiki 唯一源。  
代价：需要 Bridge 和同步一致性机制。

### ADR-004：Graphify 后台自动任务化

决策：Cherry Web 后台自动调用 Graphify Worker（Python API + LLM 语义提取，见 Doc 22 勘误）。  
理由：用户不需要手工操作 CLI，平台能审计和编排。  
代价：需要任务队列、容器环境、输出解析和失败恢复。

### ADR-005：Phase 1-3 用 PostgreSQL 图谱表，Neo4j 可选

决策：Phase 1-3 不强制 Neo4j。  
理由：降低部署复杂度。  
代价：复杂图查询性能和语法能力有限。

### ADR-006：Phase 1 用 pgvector，后续可替换 Qdrant

决策：Phase 1 优先 PostgreSQL + pgvector。  
理由：简化部署。  
代价：大规模向量性能有限。

### ADR-007：Docmost Fork 开源版 + 自建 Bridge

决策：Fork `docmost/docmost` 开源版，仓库放在 `external/docmost/`，新增 `/api/internal/bridge/` 路由组和 page save webhook。  
理由：内部小团队使用、源码全公开、企业版 ROI 不足，且需要自定义 Graphify Wiki 同步。  
代价：需要维护 Fork，与 upstream rebase 有冲突成本。

### ADR-008：源码全部公开，AGPL 风险降级

决策：CherryGraph Studio 及 Fork 修改源码全部公开。  
理由：直接满足 AGPL 网络交互场景的源码提供义务。  
代价：不能把自研差异作为闭源资产。

### ADR-009：Phase 1 不接入 Docmost

决策：Phase 1 先实现 Cherry Web 内置只读 Wiki；Docmost Fork 进入 Phase 2。  
理由：降低首期关键路径，把 Graphify 自动生成、Wiki 发布、检索和 Chat 引用先跑通。  
代价：Phase 1 只能只读浏览和管理发布，不能多人协作编辑。
